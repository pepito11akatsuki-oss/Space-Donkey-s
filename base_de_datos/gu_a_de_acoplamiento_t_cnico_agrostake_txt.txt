1. BASE DE DATOS (POSTGRESQL 15+)
--------------------------------------------------------------------------------

1.1 Agregar tabla intermedia parcel_crops (Faltante detectado)
El esquema v3.2 permite guardar evaluaciones historicas (recommendation_results),
pero no cuenta con una tabla para registrar que cultivo(s) tiene sembrados o
planificados actualmente una parcela. Ejecutar esta migracion con su politica
Row-Level Security (RLS):

CREATE TABLE parcel_crops (
    id          UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    parcel_id   UUID NOT NULL REFERENCES parcels(id) ON DELETE CASCADE,
    crop_id     INTEGER NOT NULL REFERENCES crops(id),
    status      TEXT NOT NULL DEFAULT 'planificado'
                CHECK (status IN ('planificado', 'activo', 'cosechado')),
    sown_at     DATE,
    created_at  TIMESTAMPTZ NOT NULL DEFAULT now(),
    UNIQUE (parcel_id, crop_id, status)
);

CREATE INDEX idx_parcel_crops_parcel ON parcel_crops(parcel_id);

ALTER TABLE parcel_crops ENABLE ROW LEVEL SECURITY;

CREATE POLICY tenant_parcel_crops ON parcel_crops
    FOR ALL
    USING (EXISTS (SELECT 1 FROM parcels p WHERE p.id = parcel_id))
    WITH CHECK (EXISTS (SELECT 1 FROM parcels p WHERE p.id = parcel_id));

1.2 Revision de alcance en alerts (Opcional segun alcance de demo)
- Estado actual: La tabla alerts exige stake_id UUID NOT NULL y restringe kind
  a ('bateria_baja', 'sin_reporte', 'lectura_fuera_de_rango', 'humedad_baja').
- Ajuste sugerido: Si desean emitir alertas climaticas para parcelas que aun
  no tienen estaca fisica vinculada, hacer stake_id nullable (DROP NOT NULL) y
  agregar parcel_id UUID REFERENCES parcels(id) ON DELETE CASCADE. Si todas las
  alertas dependeran de estacas fisicas, no es necesario tocar esta tabla.

1.3 Seguridad de conexion (RLS) y catalogos semilla
- Usuario de conexion de las APIs: El rol de PostgreSQL con el que se conecten
  los backends NO debe ser superusuario ni tener el atributo BYPASSRLS. De lo
  contrario, las politicas multi-tenant (app_org_id()) seran ignoradas.
- Carga de semillas minimas: Verificar que antes de iniciar pruebas esten
  pobladas las tablas:
  * crops (con source_id apuntando a data_sources)
  * crop_requirements (para soil_temperature, soil_ph, rainfall)
  * crop_irrigation_params (para que v_crop_moisture_range calcule humedad)
  * advice_rules (para soil_temperature, soil_ph y rainfall, ya que v3.2 solo
    precarga las reglas de soil_moisture)

2. BACKEND 1 - AUTENTICACION Y SEGURIDAD
--------------------------------------------------------------------------------

2.1 Claims obligatorios dentro del JWT
Al emitir el token de acceso tras el login, el payload del JWT debe incluir
exactamente estos campos para que el Backend de Negocio inyecte
SET LOCAL app.org_id en cada transaccion:

{
  "sub": "8f14e45f-ea3c-4b2a-9c1d-1234567890ab",
  "org_id": "3fa85f64-5717-4562-b3fc-2c963f66afa6",
  "role": "owner",
  "exp": 1794690000
}

- sub    : UUID correspondiente a users.id.
- org_id : UUID correspondiente a users.org_id.
- role   : Valores validos del ENUM user_role ("owner", "agronomist", "viewer").

2.2 Uso obligatorio de funciones SECURITY DEFINER
Como las tablas organizations y users tienen RLS activo (id = app_org_id()),
cualquier INSERT o SELECT directo fallara antes de iniciar sesion. Backend 1
debe usar las funciones ya creadas en el SQL:

- Registro de organizacion y usuario inicial:
  SELECT * FROM auth_register_owner(:org_name, :email, :password_hash, :full_name);

- Busqueda de usuario en login:
  SELECT * FROM auth_get_user_by_email(:email);

3. BACKEND 2 - INGESTA IOT Y CLIMA (NASA POWER)
--------------------------------------------------------------------------------

3.1 Ingesta de telemetria de estacas (soil_readings y stakes)
- Idempotencia: Insertar usando (stake_id, msg_id) con
  ON CONFLICT (stake_id, msg_id) DO NOTHING para evitar duplicados ante reenvios
  BLE o MQTT.
- Actualizacion de estado vivo: En la misma transaccion donde se inserta la
  lectura, actualizar la tabla stakes:

  UPDATE stakes
  SET last_seen_at = GREATEST(COALESCE(last_seen_at, :measured_at), :measured_at),
      last_transport = :transport
  WHERE id = :stake_id;

  Motivo: El servicio de alertas consulta stakes.last_seen_at para detectar
  estacas desconectadas (sin_reporte).
- Sensores con fallo: Si la estaca envia un error en temperatura o humedad,
  guardar NULL en PostgreSQL, NUNCA 0, para no alterar el promedio de
  soil_window().

3.2 Ingesta climatica (weather_daily y climate_cells)
- Celdas MERRA-2 ($0.5^\circ \times 0.625^\circ$): Vincular los datos al
  climate_cells.id obtenido mediante SELECT * FROM nasa_grid_center(:lat, :lon);
  para que coincida con parcels.climate_cell_id.
- Limpieza de valores faltantes (-999): NASA POWER envia -999 cuando aun no
  consolida el dato satelital (~2 dias de latencia). El esquema tiene
  CHECK (precip_mm >= 0), por lo que todo -999 debe convertirse a NULL antes
  del INSERT.
- Ventana de re-descarga: En cada ejecucion diaria, hacer UPSERT
  (ON CONFLICT (cell_id, obs_date) DO UPDATE) de los ultimos 7 dias para
  rellenar los dias que previamente llegaron como NULL.

3.3 Simulador de pH (soil_ph_observations)
- Cada registro generado por simulacion debe guardarse con method = 'simulado'
  y source_id apuntando a 'Simulador de pH AgroStake' en data_sources. La vista
  latest_soil_ph tomara automaticamente el registro mas reciente por parcela.

4. MOTOR AGRONOMICO / INTELIGENCIA ARTIFICIAL
--------------------------------------------------------------------------------

PostgreSQL ejecuta restricciones CHECK y triggers diferidos (check_variables_ok)
al guardar una evaluacion. Si la respuesta de la IA viola alguna de estas
reglas, la base de datos abortara toda la transaccion.

4.1 Reglas estrictas de validacion
1. Siempre 4 variables: Cada cultivo evaluado debe devolver exactamente:
   soil_temperature, soil_moisture, soil_ph y rainfall.
2. Datos faltantes = not_evaluated (Nunca 0): Si una variable llega en null
   desde el Backend de Negocio (ej. lluvia con cobertura $< 80\%$ o parcela sin
   lectura de pH), la IA debe responder "measured": null y
   "status": "not_evaluated". Una variable en not_evaluated NO suma en
   variables_ok.
3. Clasificacion determinista:
   - variables_ok == 4  -> "recomendado"
   - variables_ok == 3  -> "condicionado"
   - variables_ok <= 2  -> "no_recomendado"
4. Trazabilidad obligatoria: Conservar sin alterar "origin": "simulado" e
   "is_simulated": true para el pH simulado, y "origin": "nasa_power" para la
   precipitacion.
5. Valor objetivo (target_value): Cuando una variable quede en "below" o
   "above", devolver el limite optimo mas cercano (optimal_min u optimal_max)
   en target_value para rellenar {target} de la tabla advice_rules.

Endpoint que expondra el Motor de IA: POST /api/v1/agronomy/evaluate

5. FRONTEND (UI/UX)
--------------------------------------------------------------------------------

- Etiquetado explicito de origen: Siempre que is_simulated == true o
  ph_method == "simulado", mostrar una etiqueta visible en la tarjeta de pH
  (ej. "Valor simulado - Demo Hacka-NASA 2026"). Para la precipitacion, mostrar
  la atribucion "Fuente: NASA POWER (MERRA-2)".
- Variables sin evaluar (not_evaluated): Cuando un check llegue con
  status: "not_evaluated" y measured: null, renderizar "Sin datos suficientes"
  y nunca reemplazar null por 0.
- Header de autenticacion: Enviar Authorization: Bearer <jwt> en todas las
  peticiones hacia /api/v1/*.
